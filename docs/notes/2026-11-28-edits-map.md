# Plan: a map of edit suggestions

Status: agreed on 2026-11-28. No milestone has started yet. See [Milestones](#milestones).

## Goals and non-goals

We visualize [`edits.parquet`](../outputs/EDITS_PARQUET.md) on the webapp's map, so that people can review the
suggested edits and debug the rules that make them. Each edit is drawn with an icon for the kind of place, from the
[Maki](https://github.com/mapbox/maki) and [Temaki](https://github.com/rapideditor/temaki) icon sets. Clicking an
edit shows what a mapper would need to perform it: the OSM element and its version, the changes with their old
and new values and reasons, the warnings, and the AllThePlaces sources with their pages.

The map also has a filtered mode that shows only the edits of one AllThePlaces spider, or of one Wikidata ID as
brand, operator or network. The webapp's spider and Wikidata pages link to it.

The tiles carry enough to build an interactive editor on later, but that editor is out of scope here. So are any
changes to the rules that make the edits, and any changes to `conflated.pmtiles`.

## Measurements

From `edits.parquet` of the 2026-11-23 planet run, measured with DuckDB:

- 1.73 million edits: 1.13 million modifies and 594,000 creates.
- 9,379 filter keys: 4,388 spiders and 4,991 Wikidata IDs. A Wikidata ID counts for an edit when it is in
  `brand:wikidata`, `operator:wikidata` or `network:wikidata` before or after the edit, so a create counts for the
  IDs it adds, and a modify for those OSM has and those it adds. A key list with `;` counts for each ID.
- Edits per key: median 50, 90th percentile 640, 99th percentile 5,400. 36 keys have more than 10,000 edits, and 2
  more than 50,000. The largest are `royal_mail_gb` (98,093), Q638098 (59,742) and `wildberries` (47,897).
- As deflated GeoJSON with the properties of [the key archive](#edits-by-keyzip), an edit takes about 27 bytes.
  `royal_mail_gb` comes to 2.4 MB deflated and 22 MB inflated, `shell` (28,328 edits) to 750 KB. The whole archive
  has 3.4 million points (an edit is in about two keys), about 90 MB.

## Design

Two new outputs, both published by `upload.rs` and listed in `datapackage.json`, both documented as visualization
aids that may change without notice, like `conflated.pmtiles`.

### `edits.pmtiles`

One global tileset with one layer, `edits`, built with Tippecanoe the way
[`conflated.pmtiles`](../outputs/CONFLATED_TILES.md) is: a coarse overview (z0–12) and a detail (z13–14), joined with
`tile-join`. Both use `tiles.rs` as it is.

- **Overview, z0–12:** one point per edit, with only `icon`, `action`, `topic` (the edit's first topic) and
  `importance`, rounded to two decimals. No `id`, since a unique value defeats the vector tile's value dedup; see
  the measurements in `CONFLATED_TILES.md`. Coarse zooms keep the most important edits with the same importance
  filter as `conflated.pmtiles`, and `--drop-densest-as-needed` thins a tile that is still too large.
- **Detail, z13–14:** every edit, with:
  - `id`, `action`, `topics` (joined with `;`), `icon`, `importance`;
  - `osm:type`, `osm:id`, `osm:version`, for modifies; an editor compares `osm:version` with the live element;
  - `changes`, the `changes` list as a JSON string, so that a removed tag (`new` null) and the `atp` value of a
    `needs_review` change survive exactly;
  - `warnings` (joined with `;`);
  - `sources`, a JSON string with each source's `spider`, `fetched` (date), `atp_ref`, `source_url`, `relation`,
    `rule` and `distance_m`;
  - `host:type`, `host:id`, `host:name`, for creates inside another place.

  Not in the tiles: `osm.tags`, `way_members` and `relation_members`. A viewer fetches the live element from the
  OpenStreetMap API when someone clicks an edit, as it does for `conflated.pmtiles` today
  ([#1026](https://github.com/brawer/osmdiffs/issues/1026)), and an editor needs the live element anyway.
- **Geometry:** a point, at the node or at a point on the surface of a way or relation. The OSM shape is not
  repeated: `conflated.pmtiles` has it, keyed by `osm:type` and `osm:id`. Where `atp_geometry` is more than 5 m from
  the point, the detail also has a line from it to the point (`part: "link"`), as in `conflated.pmtiles`.

Icons need no other thinning than dots. An icon is a string out of a few hundred, so it costs about as much in a tile
as a dot. How much room it takes on screen is up to the renderer: the webapp draws a circle for every edit and a
symbol layer above it with `icon-allow-overlap: false` and `symbol-sort-key` by importance, so MapLibre hides the icons
that collide, and their dots stay.

### `icon`

An edit's icon is the Maki or Temaki name, such as `maki-cafe` or `temaki-vending_machine`, of the
[id-tagging-schema](https://github.com/openstreetmap/id-tagging-schema) preset that best matches the element's tags
after the edit. id-tagging-schema is ISC-licensed and published on npm, so the pipeline downloads it the way it
downloads the name-suggestion-index, and records it in the CycloneDX BOM. Matching follows iD's rules in a simplified
form: the preset with the most matching tags in `tags` wins, ties are broken by `matchScore`. An edit without a match
gets an empty `icon`, and the webapp draws its dot only. Maki and Temaki are CC0.

### `edits-by-key.zip`

The filtered mode needs every edit of one key at every zoom, and the global tileset has only some of them at coarse
zooms. Most keys are small, and the largest has under 100,000 edits, which MapLibre's GeoJSON source tiles in its
worker within a second or two. So the filtered mode loads all edits of the key and renders them in the browser. No key
gets tiles of its own.

The archive is a standard ZIP with one deflated entry per key:

- `spider/<spider>.geojson` and `wikidata/<Q-id>.geojson`: a FeatureCollection of points with `id`, `action`,
  `topics`, `icon` and `importance`. Coordinates are rounded to 1e-7 degrees.
- `index.json`, the first entry: for each key, the offset and length of its entry's deflated data (not of its local
  header, whose length varies), the number of edits and the bounding box.

The webapp reads `index.json` with one range request for the start of the file, then one range request per key, and
inflates the data with the browser's `DecompressionStream('deflate-raw')`. It never needs the ZIP's central directory,
but `unzip -l` and `unzip -p` still work for debugging. To show a clicked edit, the webapp fetches the z14 tile of
`edits.pmtiles` at its position and finds the feature by `id`, so the archive needs no detail of its own.

Should a key ever grow past about 200,000 edits, it would get a PMTiles entry of its own, built by Tippecanoe with
the overview's settings and stored without compression, and `index.json` would say so. `pmtiles` reads such an entry
through a custom `Source` that adds the entry's offset. We build this only when a key needs it.

### Deletes

Once deletes come back ([#1044](https://github.com/brawer/osmdiffs/issues/1044)), they go into both outputs with
`action: "delete"`, and the webapp draws them with a ring of their own. The design has nothing else to change for
them.

## Alternatives considered

- **One Tippecanoe run per key.** 9,379 runs, most for a few dozen points, each writing tiles from z0 to z14. Nothing
  needs these tiles: even the largest key renders fine in the browser.
- **One global tileset, filtered by key in the style.** The coarse zooms are thinned for all keys alike, so a filtered
  map shows few of a key's edits there. This is the problem that `spider_cells` works around in `conflated.pmtiles`.
- **Our own point-thinning tiler in Rust.** Only needed if we had per-key tiles.
- **FlatGeobuf per key.** It doesn't compress and needs more bytes per feature; its spatial index only pays off for
  files much larger than a key's. The webapp would still convert the features for MapLibre.
- **PMTiles per key with leaf tiles only, thinned in the browser.** MapLibre can overzoom a tile but not underzoom
  it, so at z3 it would need every leaf of the key, hundreds of requests for a key spread over the world.

## Milestones

Each step is one PR. Pipeline PRs are in `osmdiffs`, webapp PRs in `osmdiffs-app`.

1. This plan.
2. `edits.pmtiles` with the layer above and an empty `icon`, its docs page `docs/outputs/EDITS_TILES.md`, and the
   `edits-tiles` resource. Measure the build time, the z0 feature count and the largest tile on the planet.
3. Webapp: draw `edits.pmtiles` as dots, with a toggle between conflation and edits, and a detail panel for a clicked
   edit, which fetches the live element and says whether it changed since `osm:version`.
4. `icon` from id-tagging-schema, with the input in the BOM. Report the share of edits without an icon.
5. Webapp: a sprite from Maki and Temaki, built at release time, and icons over the dots.
6. `edits-by-key.zip`, its section in `EDITS_TILES.md`, and the `edits-by-key` resource.
7. Webapp: the filtered mode, linked from the spider and Wikidata pages, and zoomed to the key's bounding box.

Milestones 2 and 6 don't depend on each other, nor do 3 and 4.
